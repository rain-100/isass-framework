# 业务价值测试规范

## 原则

测试必须防止明确的业务或框架故障。新增或保留测试前，应能说明它保护的规则、边界或历史缺陷；无法说明时，不应让该测试成为长期维护负担。

优先保留和编写以下测试：

- 安全暴露面、认证和权限判定；
- 事务提交、失败回滚、生命周期时机和外部副作用边界；
- 幂等、并发、租户或数据隔离；
- DDL 可执行性、唯一约束和生成器的稳定语义；
- 真实输入输出合同、序列化、协议兼容和历史故障回归；
- 框架公共机制的关键边界与业务项目中可观察的业务结果。

## 不应编写或保留的测试

- 手工维护全量 Entrypoint、权限、资源、Bean、类名、方法名或固定数量清单；
- 因新增正常业务接口、权限或实现类而要求同步测试夹具清单；
- 只验证常量、简单 getter/setter、构造器赋值、代码能够编译或 Spring Bean 存在；
- 不附带条件地验证某个 mock 方法恰好调用一次；
- 在业务项目中重复框架已经覆盖的解析、序列化、路由或通用工具实现快照。

测试可以校验一组业务能力是否完整，但必须以业务不变量表达，例如“匿名用户不能获得管理权限”或“附件编辑权限必须包含四个标准写入口”，不能退化为“当前所有类名和方法名必须与手写列表完全一致”。

## 修改测试时的检查

1. 写明该测试能发现的具体故障；
2. 判断应由框架测试还是业务测试承担；
3. 断言外部可观察行为，避免锁定无业务意义的内部结构；
4. 删除低价值测试时，确认其未覆盖安全、回滚、并发、数据隔离或历史缺陷。

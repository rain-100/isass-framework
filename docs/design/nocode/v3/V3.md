# NoCode V3 架构

## 总览

NoCode V3 使用“每个实体一个强类型 Controller”的运行时模型。代码生成器为实体、Criteria、Service、Repository 和 Controller 生成静态 Java 类型，Spring MVC 直接完成请求体反序列化和 query 参数绑定。

接口文档由 Smart-Doc 根据这些强类型接口和 Javadoc 生成。文档服务随后把各实体重复的 V3 路径折叠成一套统一接口，Knife4j 通过实体下拉框选择具体 Schema。运行时仍访问具体实体 Controller，不存在动态 Controller 转发。

```text
HTTP request
  -> V3<Entity>Controller
  -> IV3Controller<E, C> default endpoint
  -> V3<Entity>Service
  -> V3<Entity>Repository
  -> V3<Entity>Mapper
```

## 生成产物

以 `IconGroup` 为例：

```text
api/nocode/model/entity/V3IconGroup.java
api/nocode/model/criteria/V3IconGroupCriteria.java
api/nocode/service/IV3IconGroupService.java
nocode/db/mapper/V3IconGroupMapper.java
nocode/db/repository/V3IconGroupRepository.java
nocode/service/V3IconGroupService.java
controller/V3IconGroupController.java
```

`V3IconGroupController` 的结构如下：

```java
@RestController
@RequestMapping("/attachment-service/iconGroup")
public class V3IconGroupController
        implements IV3Controller<V3IconGroup, V3IconGroupCriteria> {

    @Getter
    @Autowired
    private V3IconGroupService service;
}
```

实体名已经写入静态路径，泛型也已具体化。这样 Smart-Doc 可以解析 `V3IconGroup`、`V3IconGroupCriteria` 以及所有 `Resp<T>` 返回值。

## IV3Controller

`IV3Controller<E, C>` 定义标准 V3 HTTP 接口并通过 `getService()` 委托到本地服务。Controller 不继承 `IV3Service`，因为 HTTP 返回类型是 `Resp<T>`，业务服务返回类型是原始业务类型。

主要约定：

- 单实体请求体使用 `@RequestBody E`。
- 批量请求体使用 `Collection<E>` 或 `List<E>`。
- Criteria 使用 `@ModelAttribute C`，作为 query 参数绑定。
- 有业务数据的方法返回 `Resp<T>`，并调用 `Resp.bizSuccess(data)`。
- 原无返回值方法返回 `Resp<?>`，并调用 `Resp.bizSuccess()`。
- GET、DELETE 等 Criteria 接口由 Spring 按字段真实类型转换数字、布尔和枚举。

接口路径由具体 Controller 的类级路径和 `IV3Service` 中的 V3 相对路径常量组成，例如：

```text
GET /attachment-service/iconGroup/v3/1/criteria
POST /attachment-service/iconGroup/v3
DELETE /attachment-service/iconGroup/v3/criteria
```

## Criteria

运行时 Criteria 保留完整查询能力。对普通等值查询，HTTP query 参数直接绑定到 Criteria 的实体字段。

API 文档只投影：

- 实体字段对应的等值条件；
- `selectColumns`；
- `orderBy`；
- 分页接口额外显示 `pageNum`、`pageSize`、`searchCountFlag`。

`Like`、`Equal`、`orXxx`、`setOr` 等增强字段不在统一文档中展示，避免参数列表膨胀；这不限制服务内部使用这些能力。

## Smart-Doc 与 Schema

Smart-Doc 配置使用：

```json
{
  "componentType": "NORMAL"
}
```

因此组件使用 `V3Icon`、`V3IconGroup` 等稳定名称，不生成随机哈希名称。

实体字段说明直接来自字段 Javadoc。V3 实体模板把数据库字段注释写入 Javadoc，Smart-Doc 再写入 OpenAPI `description`。不使用 Swagger 注解、自定义 Schema 注解或 `FIELD_DESCRIPTIONS` 运行时描述表。

## OpenAPI 折叠

Smart-Doc 原始文档包含每个实体的完整路径。`V3OpenApiEnhancer` 按“HTTP 方法 + `/v3` 后缀”分组，例如：

```text
GET /attachment-service/icon/v3/1/criteria
GET /attachment-service/iconGroup/v3/1/criteria
```

折叠为：

```text
GET /{serviceName}/{entityName}/v3/1/criteria
```

增强器执行以下处理：

- 删除文档中的实体专用 V3 paths；
- 保留 Smart-Doc 生成的命名 Schema；
- 请求体用 `oneOf` 表达不同实体，批量请求使用 `items.oneOf`；
- 响应以各实体对应的 `Resp` Schema 组成 `oneOf`；
- Criteria 字段从命名实体 Schema 的 `properties` 读取；
- 输出 `x-isass-oneof-mapping` 和 `x-isass-criteria-parameters` 供 Knife4j 切换实体。
- 折叠后的标准接口统一使用“V3零代码接口”分组。
- 删除 `V3<Entity>Controller` 技术分组；没有手写接口的实体 Controller 不会显示。
- 存在手写接口的实体 Controller 使用数据库表注释生成的中文 `@tag` 分组。
- 折叠接口的 `operationId` 使用 `v3_` 前缀，避免与 V2 Controller 方法重名。
- 接口标题统一使用“动作-参数-结果”，例如“增-批量”“查-根据id-单体”“查-根据条件-分页列表”。
- `IV3Controller` 方法使用 Smart-Doc `@order`，按增、改、查、删四组定义顺序。
- Smart-Doc 的 OpenAPI 产物不包含 Knife4j 所需的 `x-order` 时，增强器只为折叠后的 V3 operation 补充等价 `x-order`；其他 Controller 顺序不受影响。

增强器不反射实体，也不重新生成字段 Schema。Smart-Doc 产物是类型和描述的唯一来源。

## Knife4j 调试

Knife4j 顶部服务列表提供 `serviceName` 候选，默认值是当前微服务。实体下拉框来自 `x-isass-oneof-mapping`。

切换实体时：

- `entityName` 同步变化；
- 请求体切换到对应命名 Schema；
- Criteria 只展示对应实体字段；
- 最终 URL 指向具体实体 Controller 的静态路径。

## 代码生成

入口：

```text
isass-nocode-core/.../generator/V3MybatisPlusGenerator.java
```

模板：

```text
isass-nocode-core/src/main/resources/v3Template/
```

生成器分为 API 产物和服务端产物。Controller 与 LocalService 一起生成到服务模块，实体、Criteria 和服务接口生成到 API 模块。

## 验证要点

- 每个实体存在一个 `V3<Entity>Controller`。
- Spring 中不存在统一动态 `V3Controller`。
- 所有 HTTP 方法返回 `Resp`。
- Criteria 参数带 `@ModelAttribute`。
- Smart-Doc 生成可读的 `V3*` Schema 名称。
- 字段 `description` 与实体 Javadoc 一致。
- `/v3/api-docs` 只展示折叠后的统一 V3 paths。
- Knife4j 的服务、实体、请求体、Criteria 和最终 URL 保持同步。

# NoCode V3 架构

## 总览

NoCode V3 以 `IV3XxxService` 作为唯一业务契约。代码生成器生成实体、Criteria、Service 接口、本地实现、持久层，以及轻量实体 Controller 扩展外壳。

```text
业务调用 -> IV3XxxService -> 本地实现 > gRPC 远程 > HTTP 远程
HTTP    -> 单个 V3HttpServerAdapter -> IV3XxxService
手写HTTP -> V3XxxController -> V3XxxService
gRPC    -> 单个 V3GrpcServerAdapter -> IV3XxxService
OpenAPI -> v3-contract.json + Smart-Doc -> 统一 V3 文档
```

本地实现存在时直接调用本地 Bean。没有本地实现时，代理按照 gRPC、HTTP 的顺序选择远程 transport。业务代码始终只依赖 `IV3XxxService`。

生成的 `V3XxxController` 不实现 `IV3Controller`，也不承载标准 CRUD 或 `IV3XxxService` 契约方法。它只用于业务微服务需要直接使用 Spring MVC 能力的手写扩展接口；这类接口由 Smart-Doc 生成普通 OpenAPI 文档。

## 模块

| 模块 | 职责 |
| --- | --- |
| `isass-nocode-core` | `IV3Service`、契约模型、路由匹配、服务代理、transport 优先级与安全回退 |
| `isass-nocode-generator` | Maven 构建期读取 Java 源码和 Javadoc，生成契约与 proto |
| `isass-nocode-http` | 单 Bean 动态 HTTP 服务端和 HTTP 远程 transport |
| `isass-nocode-grpc` | 单 Bean 动态 gRPC 服务端、逻辑方法描述和 gRPC 远程 transport |

## 构建期契约

API 模块配置 `isass-nocode-generator:generate` 后，在 `generate-resources` 阶段生成：

```text
META-INF/isass/v3-contract.json
proto/<application>-v3.proto
```

契约包含：

- 微服务名、实体名、服务接口、实体与 Criteria Java 类型；
- 标准 CRUD 和自定义业务方法；
- HTTP 方法、路径、参数来源、返回类型、顺序及幂等属性；
- 实体 Schema 名、字段类型及字段 Javadoc。

实体字段描述直接读取 Javadoc，不需要 Swagger、Schema 或自定义运行时注解。

## 自定义业务方法

业务方法直接添加到 `IV3XxxService`。Javadoc 可声明 HTTP 方法、路径和文档顺序：

```java
/**
 * 查询租户可用图标
 *
 * @param tenantId 租户 ID
 * @http GET /available/{tenantId}
 * @order 501
 */
List<V3Icon> findAvailableIcons(Long tenantId);
```

未声明 `@http` 时默认使用 `POST /action/{methodName}`。路径变量参数记为 path；GET、DELETE 的其他参数记为 query；其余参数记为 JSON body。多个 body 参数使用以参数名为字段名的 JSON 对象。

## 动态 HTTP

`V3HttpServerAdapter` 是所有实体共用的唯一 Spring Controller Bean：

```text
/{serviceName}/{entityName}/v3
/{serviceName}/{entityName}/v3/{operationPath}
```

适配器根据契约匹配逻辑操作，完成 path、query、body 类型转换，调用本地 `IV3Service`，并统一返回 `Resp`。GET、DELETE 的 Criteria 来自 query 参数；String、数字、布尔、枚举等值由 Jackson 按 Criteria 字段真实类型转换。

Criteria 文档只展示实体等值字段、`selectColumns`、`orderBy`；只有分页操作额外展示 `pageNum`、`pageSize`、`searchCountFlag`。`Like`、`Equal`、`orXxx`、`setOr` 等增强条件不进入 HTTP 文档。

## 动态 gRPC 与观测

Spring 中只注册一个 V3 gRPC 适配器，不为每个实体创建实现 Bean。适配器仍为每个服务方法注册独立的原生 `MethodDescriptor`，例如：

```text
vip.isass.attachment.v3.IconService/Add
vip.isass.attachment.v3.IconService/FindAvailableIcons
```

因此 gRPC 日志、指标、链路追踪和服务网格能够按真实接口区分调用，不会全部聚合成 `V3Transport/invoke`。构建生成的 proto/stub 是类型产物，不注册为 Spring Bean。

## 调用优先级与安全回退

调用优先级固定为：

```text
本地实现 > gRPC 远程实现 > HTTP 远程实现
```

回退规则：

- transport 不可用、预检失败或熔断器已打开时，可以选择下一 transport；
- 非幂等操作的 gRPC 请求一旦发出，失败后禁止再通过 HTTP 重试；
- 只有契约明确标记为幂等的查询，才允许在请求发出后跨 transport 回退。

这样可避免新增、修改、删除操作因跨协议重试而执行两次。

## OpenAPI 与 Knife4j

Smart-Doc 只负责普通手写 Controller。V3 文档增强器读取 `v3-contract.json`，生成：

- `V3Icon`、`V3IconGroup` 等稳定命名 Schema；
- 来自实体字段 Javadoc 的 `description`；
- `/{serviceName}/{entityName}/v3/**` 统一路径；
- 请求与响应 `oneOf`；
- `x-isass-oneof-mapping` 和 `x-isass-criteria-parameters`；
- `v3_` 前缀 operationId；
- “增、改、查、删”顺序和“动作-参数-结果”标题。

Knife4j 切换实体时同步更新 `entityName`、请求 Schema 和 Criteria 字段；`serviceName` 默认当前微服务，也可从顶部服务列表选择。

## 生成产物

以 `IconGroup` 为例：

```text
api/model/entity/V3IconGroup.java
api/model/criteria/V3IconGroupCriteria.java
api/service/IV3IconGroupService.java
db/mapper/V3IconGroupMapper.java
db/repository/V3IconGroupRepository.java
service/V3IconGroupService.java
controller/V3IconGroupController.java
```

`V3IconGroupController.java` 是手写 Spring MVC 扩展外壳，不实现 `IV3Controller`，也不包含标准 V3 CRUD。

## 验证要点

- 业务代码只注入 `IV3XxxService`；
- 实体 V3 Controller 只承载手写扩展接口，不承载标准 V3 CRUD；
- 构建自动生成契约和包含全部服务的 proto；
- HTTP 只使用一个动态适配器；
- gRPC 每个逻辑方法有独立原生方法名；
- OpenAPI 保留普通 Controller，同时生成完整统一 V3 文档；
- 字段说明与实体 Javadoc 一致；
- transport 选择与安全回退符合上述规则。
